# kid-laptops CI on Frank — implementation plan

**Spec:** `docs/superpowers/specs/2026-07-26--cicd--kid-laptops-tekton-ci-design.md`
**Answers:** `derio-homelab/kid-laptops` issue #43
**Companion spec:** `docs/superpowers/specs/2026-07-26--virt--kubevirt-vms-design.md`

## What this builds

The cluster-side half of kid-laptops' first Tekton build — everything that does
not need a hypervisor. A push to GitHub mirrors into Gitea, the mirror's push
creates a PipelineRun in `kid-laptops-ci`, and that run lints, syntax-checks and
unit-tests the pushed commit.

## What this deliberately does not build

KubeVirt. It is absent from Frank entirely — no CRDs, no operator — so the
molecule stage of kid-laptops' pipeline cannot run and is gated off rather than
left to fail. The hypervisor is designed in the companion spec and deployed by
its own plan.

This is the operator's call and it is the right one: a pipeline that always ends
red teaches nobody anything, and a green pipeline is genuinely useful for the
Python and Ansible half of that repo today.

## The honesty problem this plan has to hold

The pipeline will be **green without testing the thing the repo exists to
test**. `roles/base` is not verified against any machine until KubeVirt lands.

Three places carry that caveat so it cannot quietly evaporate:

1. the acceptance row is scoped to the Python half only, and deliberately does
   not reuse kid-laptops' broader `every-push-runs-ci-pipeline` id;
2. the report on #43 says which of their three rows this does and does not
   satisfy, and asks them not to flip any;
3. the spec's Named Gaps section leads with it.

## Order and why

Phases 1 and 2 are independent roots — namespace/RBAC and the mirror credential
touch nothing in common. Phase 3 fans in from both because the TriggerTemplate
needs the namespace to exist and the CI trigger is meaningless without the
mirror that feeds it.

Phase 4 (the kid-laptops PR) runs after 3 so the pipeline changes and the
coordinates it must agree with are decided. It works in a scratch clone under
`/tmp`; kid-laptops content is never vendored into frank.

Phase 5 is documentation and runbook sync.

Phase 6 is manual and last, with nothing depending on it — per fr-goal's
back-loading policy. One part of it is unusually pre-merge: the GitHub App
installation id genuinely cannot be known by an agent (no App is installed on
`derio-homelab` today — verified, the installations list is empty), and merging
with the sentinel in place would leave a permanently failing ExternalSecret
while ArgoCD reported green. That is the exact shape of a bug that once hid for
seven days, so the operator fills it on this PR before merge.

## Two defects this plan fixes that the request did not know about

**The generic trigger double-fires.** `gitea-listener`'s catch-all `gitea-push`
trigger filters only `!full_name.startsWith('agentic-stoa/')`. A
`derio-homelab/kid-laptops` push therefore matches it as well as its own new
trigger, producing two PipelineRuns per push — one of them the generic
`gitea-ci` pipeline, failing. Phase 3 subtracts the prefix and a tripwire keeps
it subtracted.

**`$(uid)` is random, not unique.** The request is emphatic that two runs
sharing a `run-id` create and destroy each other's VM. Tekton documents `$(uid)`
as "a random value, just like the postfix generated by `generateName`" — which
is not a uniqueness guarantee. The `run-id` is therefore `<short-sha>-$(uid)`,
which also makes a VMI name traceable back to a commit.

## Manual operations

```yaml
# manual-operation
id: cicd-kid-laptops-github-app-install
layer: cicd
app: tekton
plan: 2026-07-26-cicd-kid-laptops-tekton-ci
when: Before merging the frank PR
why_manual: >-
  Installing a GitHub App into an org is a UI/consent action, and the resulting
  installation id cannot be known or guessed by an agent. Verified absent:
  `gh api /orgs/derio-homelab/installations` returns an empty list.
commands:
  - Install App derio-fr-automation (3994132) into org derio-homelab, scoped to
    the kid-laptops repository only.
  - env -u GITHUB_TOKEN gh api /orgs/derio-homelab/installations --jq '.installations[].id'
  - Replace REPLACE_AFTER_APP_INSTALL in
    apps/tekton/manifests/clustergenerator-derio-homelab-github-app.yaml and
    push to the same PR.
verify:
  - kubectl -n tekton-pipelines get externalsecret derio-homelab-github-mirror
    -o jsonpath='{.status.conditions[0].reason}' — SecretSynced
status: pending
```

## Test plan

The spec's Test Plan is post-merge and operator-driven; phase 6 task 3 executes
it. Its sharpest assertion is step 4: **exactly one** PipelineRun per push. Two
means the generic-trigger exclusion regressed, and that is a defect which
otherwise announces itself only as an unrelated-looking failing run.
