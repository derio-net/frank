# Scope AI-agent cluster access down from cluster-admin

**Date:** 2026-11-14
**Layer:** auth
**Status:** Draft
**Issue:** derio-net/frank#912 (blocks the credential steps of #913, plan step P7.T1.S1)

## Context

#912 asks that no AI-agent identity hold `cluster-admin`, so that #913's session
credentials (Omni upgrade key, Hop kubeconfig, session GitHub App PEM, tailscale
keys) can land in `upgrade-sessions` / `cluster-update-fr` without an agent being
able to read them. Admission policies cannot block reads, so this has to be RBAC.

Half is done: `secure-agent-pod/agent-sa` and its `secure-agent-pod-cluster-admin`
binding were deleted by #950 Phase 2.

### What was measured (2026-11-14, read-only, Authentik ORM)

| Fact | Value |
|---|---|
| Members of `root-agents` | **none** |
| Members of `root-admins` (superuser group, bound to `cluster-admin`) | `claude-agent` (**service account**, the `k8s-agent` client-credentials identity) and `akadmin` |
| Members of `root-devops`, `root-developers` | none |
| `k8s-agent` provider scope mappings | `openid`, `email`, `profile`, `offline_access`; the `profile` mapping **emits a `groups` claim** |
| 2026-08-02 live TokenReview of a `k8s-agent` token | groups `[system:authenticated]` only (from `net-oidc-cutover-continuity`) |

Reading it together:

1. The `authentik-root-agents` -> `cluster-admin` binding grants **nothing today**,
   because the group is empty. Scoping it down is necessary hygiene but does not
   by itself change what any identity can do.
2. The AI identity (`claude-agent`) is in `root-admins`, not `root-agents`. Its
   August token carried no groups, so the claim is only emitted when the token
   request asks for the `profile` scope. Which Authentik user a `k8s-agent` token
   belongs to depends on how it is requested: client id and secret alone give the
   provider's synthetic `ak-Kubernetes Agent Access-client_credentials` user (the August
   TokenReview), while a service account's username and app-password token give that
   service account, `claude-agent`. The repo cannot show which the operator uses, so
   the live token review is run in the second mode, which is the one that matters. A client holding that credential can ask
   for it and receive `root-admins`, which is `cluster-admin`. **That is the real
   hole behind #912**, and the issue text (which names `root-agents`) misses it.
3. A fresh TokenReview was not run: `.env_agent` is not on this machine, and the
   alternative was reading the provider's client secret from the cluster, which
   this change does not need. The Authentik state above is the evidence; the post-merge
   walk re-proves it live with a `root-agents`-shaped SubjectAccessReview.

### Mechanics that shape the design

- `roleRef` is immutable, so the old binding cannot be edited into a scoped one.
- Every app runs `prune: false`: deleting `authentik-root-agents` from git leaves
  it live. It needs a manual `kubectl delete` (same trap as the `*-frank` routes).
- RBAC cannot exclude namespaces from a ClusterRoleBinding, so a namespaced read
  that must skip three namespaces is bound per namespace.
- `kubectl auth can-i --as/--as-group` is vacuous through the Omni proxy (#963);
  only a server-side SubjectAccessReview with a `system:masters` control proves access.
- Group membership lives in Authentik, not in a blueprint (`blueprints-groups.yaml`
  declares the groups with no members), so moving `claude-agent` is a live operation.

## Requirements

R1. Members of Authentik group `root-agents` receive cluster-scoped read only: a new ClusterRole `root-agents-cluster-read` (nodes, namespaces, persistentvolumes, storageclasses, customresourcedefinitions; get/list/watch) bound by a new ClusterRoleBinding `authentik-root-agents-read`.
R2. Members of `root-agents` receive namespaced read through a dedicated ClusterRole `root-agents-ns-read` (an explicit resource list, no wildcards, no Secrets, no aggregation labels) via one generated RoleBinding per Frank app namespace, never in `upgrade-sessions`, `cluster-update-fr` or `runs-fr`, and none in the credential-store namespaces `authentik`, `infisical`, `argocd`, `kube-system` and `longhorn-system` (amended 2026-11-14 by operator decision: pod specs, pod logs and ConfigMaps there can carry credentials, so the read is withheld, not only Secrets).
R3. `root-agents` holds no write verb anywhere and no `impersonate`, `serviceaccounts/token`, `escalate`, `bind` or `secrets` access, and no right in `upgrade-sessions`, `cluster-update-fr` or `runs-fr`.
R4. The `authentik-root-agents` -> `cluster-admin` binding is removed from git and deleted from the cluster, after the new bindings are proven by a SubjectAccessReview matrix.
R5. No AI-agent identity holds `cluster-admin`: the `claude-agent` service account moves from `root-admins` to `root-agents` (a live Authentik change, recorded as a manual operation).
R6. The RoleBindings are generated by `scripts/root_agents_rbac.py` from the app destinations of the Frank root chart only (keys `frank/*`, in-cluster destination), with a `--check` mode, so the set follows the repo and never names a Hop namespace.
R7. A CI guard under `scripts/tests/` fails when the generated file is stale, when any namespace in the protected set is bound for `root-agents`, when any Group subject outside `root-admins`, `root-devops`, `system:masters` can read Secrets in a protected namespace, or when a ServiceAccount outside an explicit allowlist (the `cluster-update-fr` console, `runs-fr` and the session ServiceAccounts, each named in the guard with its reason) can, or when a `root-agents` rule grants a forbidden verb or resource.
R8. The docs and tests that describe `root-agents` as a cluster-admin gap are updated in the same PR (see Design, Coupled files).
R9. Before and after the cutover, a SubjectAccessReview matrix proves the intended allow and deny cells, each beside a `system:masters` control that must answer allowed, and a revert path (re-apply the old binding from git history, re-add `claude-agent` to `root-admins`) is documented in the manual operation.

## Design

### Manifests (`apps/authentik-extras/manifests/`)

- `k8s-rbac.yaml`: drop `authentik-root-agents` (cluster-admin). Add the ClusterRole
  `root-agents-cluster-read` and ClusterRoleBinding `authentik-root-agents-read`.
- `root-agents-ns-read` ClusterRole (in `k8s-rbac.yaml`): get/list/watch on an
  enumerated set of core, apps, batch, networking, argoproj and longhorn kinds
  (pods, pods/log, services, endpoints, configmaps, events, PVCs, workloads, jobs,
  Applications, Rollouts, Longhorn volumes). Not the built-in `view`: `view`
  aggregates every `aggregate-to-view` role operators ship, so its reach cannot be
  stated statically. Nothing in it names `secrets`, `*`, `impersonate`, `bind`,
  `escalate` or `serviceaccounts/token`.
- `root-agents-rbac.yaml` (GENERATED, `scripts/root_agents_rbac.py --write`):
  RoleBinding `root-agents-ns-read` in each namespace, subject Group `root-agents`,
  roleRef that ClusterRole. The namespace set takes the `scripts/life_sessions._destinations()`
  keys that start with `frank/` (it also yields `hop/*` keys such as `caddy-system`,
  which do not exist on Frank), minus `PROTECTED = {upgrade-sessions,
  cluster-update-fr, runs-fr}` and `EXCLUDED = {authentik, infisical, argocd, kube-system,
  longhorn-system}`. Agents get NO read in the five excluded credential stores (first
  design: read without Secrets; reversed 2026-11-14 once two reviewers flagged that logs
  and literal pod env can carry credentials), and the matrix proves pods, pod logs and
  ConfigMaps are denied there as well as Secrets. A new app namespace is denied until the file is
  regenerated; the CI guard fails the PR that adds one without regenerating.

A RoleBinding to a namespace that does not exist yet fails that sync, the same
exposure `apps/upgrade-sessions/manifests/app-roles.yaml` has. The pre-merge
step lists the live namespaces against the generated set.

### Guard (`scripts/tests/test_root_agents_rbac.py`)

Static over the repo's RBAC manifests (every ClusterRole/Role, binding, and the
generated file): resolves each binding to the rules it grants, expands the
`admin`/`cluster-admin` built-ins from a small table (the `root-agents` roles are explicit,
so nothing aggregated is assumed), follows Role and ClusterRole references from bindings,
and asserts R7. The
live proof is the SAR matrix, not CI.

### Cutover (manual operation, `devops` gate)

1. Merge the PR; ArgoCD applies the new bindings. The old binding still exists.
2. Operator adds the same check on live: `kubectl get ns` covers the generated set.
3. Check what `claude-agent` uses its Authentik superuser status for (API calls with its
   token): leaving `root-admins` drops `is_superuser`, not just the kube binding.
4. SAR matrix BEFORE for group `root-agents` and group `root-admins`.
5. Authentik ORM: add `claude-agent` to `root-agents`, then remove it from `root-admins`.
   This comes BEFORE the delete so the two changes are separable in the matrices. Tokens
   already issued keep their old groups claim until they expire (8 h): mint a fresh
   `k8s-agent` token from the operator's `.env_agent` and TokenReview it (groups must be
   `root-agents` or absent, never `root-admins`), in one pipeline, never printing it.
6. `kubectl delete clusterrolebinding authentik-root-agents`.
7. SAR matrix AFTER (cells below), each with the `system:masters` control.
8. Revert (any step failing): `kubectl apply` the old binding from `git show main~1:...`,
   and re-add `claude-agent` to `root-admins`.

SAR matrix, group `root-agents`: allowed = get pods and pods/log in `monitoring`, list nodes, get
`configmaps` in `monitoring` (both taken from the generated file, not typed by hand); denied = get pods, pods/log and `configmaps` in each of `argocd`, `infisical`, `authentik`, `kube-system`, `longhorn-system`; get `secrets` in `argocd`, `infisical`, `authentik`, `kube-system`, `longhorn-system`, `upgrade-sessions`,
`cluster-update-fr`, `runs-fr`; list pods in `upgrade-sessions`; create `pods`
anywhere; `impersonate` users; create `serviceaccounts/token`; `bind`/`escalate`
clusterroles.

### Out of scope

Hardening what `root-admins` and `root-devops` (human, trusted by the 2026-11-01
operator decision) can read; Authentik group-membership management as code; the
#913 phase 7 credential steps, which this unblocks.

## Verification

strategy: live
gate: devops

- root-agents-no-secrets: live — the claim is a property of the running API server's RBAC, provable only by SubjectAccessReview, and the live matrix is the issue's own done-when.
- root-agents-read-only-triage: live — needs the live bindings and namespaces.
- no-ai-agent-cluster-admin: live — Authentik membership exists only in the running Authentik database.
